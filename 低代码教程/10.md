# 一、本篇目标

上一节已经完成了代理端 Web 工作应用的创建，并通过云函数实现了代理身份认证。

代理登录后，系统可以通过当前登录用户的 `user_id`，识别对应的代理业务记录。

本篇开始开发代理端的实际业务功能：我的客户。

在设计客户列表时，我们需要解决一个问题：

代理登录后，只能看到分配给自己的客户，而不能看到其他代理的客户。

最直接的想法，是页面加载时先通过 `user_id` 查询代理记录，取得代理记录 ID，再根据代理 ID 查询客户。

但是，这种方式需要先后执行两次查询。如果直接让表格加载客户数据，可能出现先加载全部客户、再根据代理身份重新筛选的情况。

本篇采用另一种方式：

**利用客户表与代理表之间的关联关系，在 WdTable 的数据筛选属性中，通过 fx 动态取得当前登录用户的 user_id，再使用关联查询过滤客户。**

这样，表格从第一次请求开始，就带有当前代理的筛选条件。

本篇完成后，实现以下功能：

1. 创建客户数据模型。
2. 建立客户与代理之间的关联关系。
3. 创建代理端我的客户页面。
4. 根据数据模型模板生成表格页面。
5. 配置代理端导航菜单。
6. 配置 WdTable 默认数据筛选条件。
7. 使用不同代理账号验证客户数据隔离。

# 二、设计客户数据模型

## 2.1 为什么客户表需要关联代理表？

前面创建代理表时，我们已经增加了 `user_id` 字段，用于保存代理绑定的微搭用户 ID。

代理表 `biz_agent` 的核心字段如下：

| 字段标识 | 字段名称 | 类型 | 说明 |
|---|---|---|---|
| `_id` | 数据标识 | 系统字段 | 代理记录唯一标识 |
| `name` | 代理姓名 | 文本 | 代理名称 |
| `phone` | 手机号 | 电话/文本 | 联系电话 |
| `user_id` | 用户ID | 文本 | 绑定微搭认证用户 |
| `status` | 状态 | 枚举 | 启用、停用 |
| `agent_level` | 代理等级 | 枚举 | 普通、银牌、金牌 |

这里需要明确两个不同的概念：

- `user_id`：用于识别当前登录的是哪个微搭用户。
- `_id`：用于识别代理表中的哪一条业务记录。

我们不能直接在客户表中使用 `user_id` 表示代理归属。

因为客户归属的是一条代理业务记录，而不是某个认证账号。

因此，客户表需要通过关联关系指向代理表。

## 2.3 创建客户与代理的关联关系

这是本篇最重要的数据模型配置。

客户与代理之间的关系是：

- 一个代理可以拥有多个客户。
- 一个客户只归属于一个代理。

因此，这是一个典型的一对多关系。

在微搭中，我们需要在客户表中创建一个多对一关联字段，关联代理表。

具体操作：
1. 添加字段，选择关联关系类型。
2. 选择多对一关联。
3. 关联的数据模型选择代理表 `biz_agent`。
4. 设置字段名称为：所属代理。
5. 字段标识设置为：`agent_id`。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/733559c583924bee8489930d1b14590f.png)

最终形成下面的关系：

```text
代理表 biz_agent
    _id
    name
    phone
    user_id
       │
       │ 一对多
       ▼
客户表 biz_customer
    _id
    name
    phone
    grade
    agent_id
```

注意：

`agent_id` 是关联关系字段，不是普通文本字段。

它保存的是代理业务记录之间的关联关系，而不是代理的 `user_id`。

这样，后续在管理端查看客户列表时，可以通过关联关系展示所属代理的姓名。

同时，代理端也可以通过关联代理记录中的 `user_id`，直接筛选属于当前登录代理的客户。

# 五、配置客户表格的默认筛选条件

页面和菜单已经准备好，接下来解决本篇最核心的问题：

**如何让代理打开页面时，表格自动只查询自己的客户？**

## 5.1 先理解查询关系

我们已经建立了两张表之间的关联：

客户表 `biz_customer`：

- `agent_id`：关联代理表。

代理表 `biz_agent`：

- `user_id`：绑定微搭认证用户 ID。

当前登录用户可以通过微搭认证上下文取得自己的 `user_id`。

因此，查询客户时，不需要先查询代理表取得代理 `_id`。

可以直接通过关联关系查询：

```text
客户表
  │
  └── agent_id（关联代理表）
          │
          └── user_id
                 │
                 └── 等于当前登录用户的 user_id
```

这就是本篇采用关联查询的原因。

## 5.2 找到 WdTable 的数据筛选属性

选中页面中的客户数据表格组件。

在右侧属性面板中找到：

数据筛选（queryCondition）

点击属性右侧的 fx 按钮，进入表达式编辑。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/4e35fb5979d14778935ff0e40ba53be9.png)


这个属性用于给表格数据查询增加默认过滤条件。

它与表格的筛选器不是同一个概念：

- 数据筛选：页面加载时就生效的查询条件。
- 筛选器：提供给用户操作的筛选控件。

我们现在配置的是数据筛选，而不是让代理自己选择所属代理。

## 5.3 设置当前登录用户 ID

在 fx 表达式编辑器中，找到微搭认证上下文。

选择当前登录用户的用户 ID 属性。

这里使用的是当前登录用户的 `user_id`，不是代理表的 `_id`，也不是客户表的 `_id`。

## 5.4 设置关联查询条件

关联查询的核心结构来自微搭官方数据模型关联关系文档。

官方多对一关联查询示例：

```javascript
filter: {
  relateWhere: {
    teacher_id: {
      where: {
        name: {
          $eq: "li"
        }
      }
    }
  }
}
```

这个查询表示：

从学生表查询数据，并且只返回关联教师姓名为 `li` 的学生记录。

套用到我们的客户业务：

- 主表：客户表 `biz_customer`
- 关联字段：`agent_id`
- 关联模型：代理表 `biz_agent`
- 关联模型过滤字段：`user_id`
- 比较值：当前登录用户的 `user_id`

最终的查询语义是：

```javascript
({
 "where": {
 },
 "relateWhere": {
    agent_id: {
      where: {
        user_id: {
          $eq: $w.auth.currentUser.userId
        }
      }
    }
 }
})
```

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/d7ee7ccee09f4bf89c20912cd9bd0049.png)


在 WdTable 的 fx 配置中，需要将上述关联查询条件转换为 `queryCondition` 所要求的数组结构。

注意：`queryCondition` 是 WdTable 的组件属性，而 `relateWhere` 是数据模型查询参数中的关联查询条件。两者不能简单地把对象直接互换。

应以当前编辑器提供的 `queryCondition` 格式为准，将关联查询条件配置进去。

如果表达式编辑器支持动态绑定当前用户属性，就将 `$eq` 的比较值绑定到当前登录用户的 `user_id`。

## 5.5 保存并验证筛选条件

配置完成后，保存页面。

使用两个不同的代理账号进行测试。

假设：

代理张三：

```text
user_id = USER_A
```

代理李四：

```text
user_id = USER_B
```

代理表中的两条记录分别绑定这两个用户 ID。

客户表准备以下测试数据：

| 客户姓名 | 所属代理 |
|---|---|
| 王同学 | 张三 |
| 刘同学 | 张三 |
| 赵同学 | 李四 |
| 孙同学 | 李四 |

分别使用两个账号打开“我的客户”页面。

预期结果：

| 登录账号 | 页面显示客户 |
|---|---|
| 张三 | 王同学、刘同学 |
| 李四 | 赵同学、孙同学 |

验证时还需要检查浏览器网络请求或数据查询结果：

- 页面首次加载时是否已经携带关联筛选条件。
- 是否出现先查询全部客户，再重新查询当前代理客户的情况。
- 当前代理是否能够看到其他代理的客户。

如果出现无条件查询，需要回到表格的 `queryCondition` 配置中排查，不能仅凭页面最终显示正确就认为配置成功。

# 本篇总结

本篇完成了代理端“我的客户”页面的基础建设。

这里最重要的不是创建一个表格，而是理解认证身份与业务数据之间的关系。

我们使用了三个不同的字段：

| 字段 | 作用 |
|---|---|
| `user_id` | 识别当前登录的微搭用户 |
| `biz_agent._id` | 识别代理业务记录 |
| `biz_customer.agent_id` | 表示客户归属于哪名代理 |

通过客户表与代理表之间的关联关系，我们可以直接根据当前登录用户的 `user_id` 查询客户，不必先单独查询代理记录，再把代理 ID 传递给表格。

这种方式减少了页面初始化时的查询步骤，也让表格的默认筛选条件更加清晰。

需要强调的是，表格默认筛选解决的是页面查询问题，不等于完整的数据安全机制。后续客户新增、编辑、客户转移等操作，仍然需要校验当前代理身份及客户归属，不能把前端筛选条件当作唯一的权限边界。

下一篇将继续完善代理客户管理，围绕客户报备、客户信息维护和跟进记录，逐步建立完整的代理招生业务流程。
