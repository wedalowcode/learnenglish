# 前言

上一篇已经完成了微搭用户认证体系和业务身份架构设计。

现在开始进入实际搭建。

首先从管理应用开始。

英语教学机构的管理人员主要有两类：

- 管理员：负责机构整体管理，包括人员、业务配置和系统管理。
- 教务：负责日常教学运营，包括学员、教练、课程、订单和排课等业务。

这两类人员都属于内部用户，可以使用同一个管理应用。

但如果直接使用微搭默认的菜单配置，就会遇到一个问题：

管理员和教务虽然拥有不同的角色权限，但是进入应用后，可能看到相同的菜单。

例如：

管理员看到了系统设置、用户管理、角色管理、学员管理等菜单；教务也可能看到这些菜单。

当教务点击没有访问权限的页面时，微搭才会提示无权限。

这不是我们希望的用户体验。

我们希望实现：

- 管理员登录后，进入管理员工作区域，只看到管理员需要的菜单。
- 教务登录后，进入教务工作区域，只看到教务需要的菜单。
- 两类人员共用一个管理应用，不重复建设。
- 页面访问权限仍然由微搭平台控制。

因此，本篇要实现的是：

**通过微搭 Auth 获取当前用户角色，通过首页分流，通过不同布局控制菜单显示。**

最终应用结构如下：

```text
管理应用
│
├── 首页
│   ├── 读取当前用户角色
│   ├── 管理员入口
│   └── 教务入口
│
├── 管理员工作区（AdminLayout）
│   ├── 系统概览
│   ├── 用户管理
│   ├── 角色管理
│   └── 系统设置
│
└── 教务工作区（AcademicLayout）
    ├── 教务首页
    ├── 学员管理
    ├── 教练管理
    ├── 课程管理
    ├── 订单管理
    └── 排课管理
```

注意：这里的菜单是本阶段的结构规划，后续具体业务模块会逐篇实现。

## 先理解微搭的角色信息


微搭提供了 Auth 认证能力，可以通过当前登录用户对象获取用户关联的角色。

点击底部的开发者工具，在里边输入：

```javascript
$w.auth.currentUser.relatedRoles
```

可以查看具体的数据结构
```javascript
[
  {
    name: "组织成员",
    roleIdentity: "internalUser",
    id: "2056905558714662914",
    envId: "lowcode-d3gp73jc13d4d6fa9"
  },
  {
    name: "默认超级管理员",
    roleIdentity: "administrator",
    id: "-1",
    envId: "nxm-test-4gaqa3a631b405bb"
  }
]
```

这里需要重点理解三个字段：

| 字段 | 含义 |
|---|---|
| name | 角色名称 |
| roleIdentity | 角色身份类型标识 |
| id | 角色唯一标识 |

这三个字段不能混为一谈。

例如：

- `administrator` 表示默认超级管理员身份。
- `internalUser` 表示内部用户身份。
- `name` 用于识别具体角色名称，例如管理员、教务等。

**特别注意：internalUser 不等于教务。**

它表示用户属于内部用户类型，并不能区分这个用户究竟是管理员还是教务。

因此，本项目采用以下判断方式：

- 管理员：判断 `roleIdentity` 是否为 `administrator`。
- 教务：判断是否包含名称为“教务”的自定义角色。

如果后续需要避免角色改名影响判断，可以使用自定义角色的 `id` 进行判断。

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/51dca11a206d4a83baf5f8802ccd3d0f.png)

```bash
$w.auth.currentUser.relatedRoles.some(
  role => role.roleIdentity === 'administrator'
)
```
这里使用了 JavaScript 数组的 `some()` 方法。

它会遍历角色数组，只要其中一个角色满足条件，就返回 `true`。

因此，即使用户同时拥有多个角色，也可以正确识别管理员身份。

# 本篇总结

本篇完成了管理应用的基础架构。

我们没有为管理员和教务创建两个独立应用，而是通过微搭 Auth 获取当前用户角色，再通过首页入口和不同布局，实现一个应用中的多角色工作区。

整个设计可以概括为：

| 层次 | 负责内容 | 实现方式 |
|---|---|---|
| 用户认证 | 确认当前用户身份 | 微搭内部用户认证 |
| 角色识别 | 判断管理员、教务 | `$w.auth.currentUser.relatedRoles` |
| 工作区入口 | 根据角色展示入口 | 首页组件显示条件 |
| 菜单控制 | 展示不同业务菜单 | AdminLayout、AcademicLayout |
| 页面权限 | 控制页面是否可访问 | 微搭角色页面权限 |
| 数据权限 | 控制数据读取和修改 | 微搭数据模型权限 |

这套架构还有一个好处：

后续如果需要增加财务、校长等管理角色，我们不需要重新建设一套应用，只需要：

1. 在微搭后台增加相应角色。
2. 配置角色可以访问的页面。
3. 在应用中增加对应工作区布局。
4. 在首页增加对应角色入口。

这样，管理应用就具备了较好的扩展能力。
