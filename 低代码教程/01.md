# 一、为什么要先设计用户体系？

开发一个企业管理系统，首先想到的通常是用户、角色和权限。

例如，一个英语教学机构可能有以下人员：

- 管理员：负责机构整体管理。
- 教务：负责学员、教师、课程和排课。
- 教练：负责授课、课堂反馈和学员学习记录。
- 代理：负责招生、客户跟进和续费。
- 家长：查看孩子的课程安排和学习情况。

如果按照传统软件的设计思路，我们可能会建立一张统一的用户表，再通过角色表、用户角色关联表、权限表等实现权限管理。

但是，使用微搭云开发时，不能完全照搬传统系统的用户设计。

微搭自身已经提供了一套用户认证和权限体系，并且不同用户类型之间存在明确的权限差异。

如果不了解这些规则就开始设计业务表，后续很容易遇到一些问题：

- 内部用户授权数量不够。
- 外部用户无法修改管理员创建的数据。
- 用户更换手机号后，原来的业务数据无法关联。
- 一个用户同时拥有教练和代理身份时，难以处理。
- 业务权限和平台权限混在一起，导致系统越来越复杂。

因此，在正式开发之前，我们需要先理解微搭的用户体系，再根据平台能力设计业务架构。

# 二、理解微搭的三种用户类型

微搭云开发提供三种用户类型：内部用户、外部用户和匿名用户。

## 1. 内部用户

内部用户由管理员在微搭云开发后台添加。

内部用户需要占用平台授权：

| 版本  | 内部用户授权数量 |
| --- | -------: |
| 个人版 |       2个 |
| 标准版 |     100个 |
| 企业版 |     100个 |

内部用户的主要特点：

- 可以由管理员在后台创建。
- 可以配置平台角色。
- 可以根据角色控制应用访问权限。
- 可以配置数据模型的访问权限。
- 可以根据权限设置查看本人、修改本人、查看全部、修改全部等数据操作范围。

需要注意，个人版不支持自定义角色，标准版以上才支持创建自定义角色。

内部用户适合什么人？

答案不是简单地按照职位高低来划分，而是应该看这个人是否需要管理机构的核心数据。

例如，教务人员虽然不是机构管理层，但是需要维护学员、教师、课程、订单、排课等全局业务数据。

这些数据通常由管理员创建，教务也需要修改和维护。

因此，教务人员更适合使用内部用户身份。

## 2. 外部用户

外部用户主要通过用户端注册，例如手机号登录或授权手机号登录。

外部用户的特点：

- 不占用内部用户授权。
- 用户通过用户端注册。
- 管理员不能像创建内部用户一样，在云开发后台直接创建外部用户。
- 可以根据平台配置分配相应的访问权限。

但是，外部用户有一个非常重要的限制：

**外部用户只能修改自己创建的数据。**

即使管理员给外部用户分配了业务角色，也不能突破这个限制。

例如：

管理员在后台创建了一条教练记录，教练使用外部用户身份登录后，即使拥有相应的数据模型访问权限，也不能直接修改这条由管理员创建的记录。

这不是简单调整角色权限就能解决的问题，而是微搭外部用户的数据操作规则。

因此，我们不能把所有业务数据都交给外部用户直接维护，也不能把所有外部用户都设计成内部用户。

## 3. 匿名用户

匿名用户不需要登录即可访问公开应用。

适合一些不涉及个人身份认证的公开页面，例如：

- 公开课程介绍。
- 机构宣传页面。
- 公开活动展示。

本项目中的管理、教练、代理和家长都涉及具体业务数据，因此不采用匿名用户作为主要业务身份。

# 三、我们的设计原则：核心人员内部化，业务参与者外部化

了解三种用户类型后，我们就可以根据实际业务划分用户身份。

英语教学机构的人员规模可能并不小。

一个机构可能有数百名兼职教练、代理人员，以及上千名家长。

如果把所有人都设置为内部用户，即使使用企业版的100个授权，也可能无法满足实际需求。

而且，教练和代理人员具有较强的流动性，没有必要为大量临时或兼职业务参与者长期占用内部用户授权。

因此，我们采用以下原则：

**核心管理人员使用内部用户，大规模业务参与者使用外部用户。**

具体划分如下：

| 应用      | 用户类型 | 业务角色   | 主要职责         |
| ------- | ---- | ------ | ------------ |
| 管理应用    | 内部用户 | 管理员、教务 | 管理机构主数据和全局业务 |
| Web工作应用 | 外部用户 | 教练、代理  | 处理授课、招生等业务   |
| 家长小程序   | 外部用户 | 家长     | 查看课程和孩子学习情况  |

这里需要特别说明：

内部用户和外部用户是微搭的平台用户类型；管理员、教务、教练、代理和家长则是我们业务系统中的角色。

两者不是同一个概念。

我们不需要为了每个业务角色都创建一套平台用户体系，而是利用微搭认证能力，再通过业务表识别用户在机构中的实际身份。

# 四、如何规避外部用户的数据修改限制？

这是整个用户体系设计中最重要的一部分。

先看一个实际场景。

机构管理员在管理应用中创建一条教练记录：

| 教练ID | 姓名  | 手机号         | 状态 |
| ---- | --- | ----------- | -- |
| C001 | 张老师 | 13800000001 | 启用 |

这条数据由管理员创建。

张老师使用手机号登录 Web 工作应用后，需要查询自己的教练资料。

但是，外部用户不能直接修改管理员创建的数据。

如果我们把教练资料更新、业务身份绑定等操作全部交给外部用户完成，就会受到微搭数据权限规则的限制。

因此，我们将业务数据操作分成两类。

## 1. 机构主数据由内部用户维护

例如：

- 学员信息。
- 教练信息。
- 代理信息。
- 家长信息。
- 课程信息。
- 订单信息。
- 排课信息。

这些数据属于机构的核心业务数据。

由管理员和教务人员在管理应用中统一维护。

外部用户不负责修改这些核心主数据。

## 2. 业务过程数据由外部用户产生

例如：

- 教练提交课堂反馈。
- 教练记录学员学习情况。
- 教练提交单词训练结果。
- 代理记录客户跟进情况。
- 家长提交学习反馈。

这些数据由实际业务参与者创建。

外部用户可以在平台允许的权限范围内维护自己创建的数据。

这样就把机构主数据和业务过程数据分离开了。

这种设计既符合微搭的权限规则，也符合真实业务管理逻辑。

## 3. 特殊数据更新通过云函数完成

还有一种情况：外部用户需要触发对机构主数据的更新。

例如，首次登录后，需要将当前微搭认证用户的 userid 写入教练业务记录。

这条教练记录可能是管理员创建的，外部用户不能直接修改。

我们可以通过云函数处理这个特殊操作。

云函数在服务端执行，可以按照配置使用具有相应数据操作权限的身份完成更新。

在本项目中，我们计划使用云函数完成首次身份绑定。

但需要注意：

云函数不能简单地相信前端提交的教练ID或手机号。它必须在服务端重新校验当前认证身份、手机号和业务记录之间的对应关系，再执行更新。

这样既能遵循微搭的数据权限规则，又能避免前端直接修改机构核心数据。

# 五、业务身份不能直接使用手机号

解决了平台用户类型和数据权限问题之后，还需要考虑一个容易被忽略的细节：

**手机号并不适合作为业务系统长期使用的身份关联标识。**

假设张老师第一次使用手机号13800000001登录。

系统根据手机号找到教练记录，并建立业务关系。

如果以后张老师更换手机号，仍然使用原来的业务记录，那么系统就可能因为手机号变化而无法找到原来的教练身份。

这会带来一系列问题：

- 无法查询原来的教练资料。
- 无法找到原来负责的学员。
- 无法查看历史课程和授课记录。
- 可能需要人工重新建立业务关系。

所以，我们需要把手机号和微搭认证身份区分开。

## 1. 手机号只负责首次身份匹配

用户第一次登录时：

1. 用户通过手机号完成微搭认证。
2. 系统获取当前登录用户的 userid 和认证手机号。
3. 根据手机号查询对应的业务记录。
4. 判断业务记录是否存在且处于启用状态。
5. 调用云函数，将 userid 写入对应业务记录。

手机号的作用是帮助系统找到正确的业务人员。

## 2. userid 负责后续身份关联

完成首次绑定之后，后续登录不再依赖手机号查询业务身份。

而是通过微搭认证上下文获取 userid，再根据 userid 查询业务记录。

例如：

| 教练ID | 姓名  | 手机号         | userid |
| ---- | --- | ----------- | ------ |
| C001 | 张老师 | 13800000001 | U10001 |

即使张老师后来更换手机号：

| 教练ID | 姓名  | 手机号         | userid |
| ---- | --- | ----------- | ------ |
| C001 | 张老师 | 13900000002 | U10001 |

userid 不变，业务身份关联也不变。

这样，手机号就只是业务联系信息，而不是业务数据的长期关联依据。

需要注意，userid 是微搭认证身份的标识，不是教练、代理或家长的业务主键。业务主键仍然由业务系统自己管理。

# 六、业务表结构设计

根据前面的设计，我们不需要额外建立一套复杂的统一用户表、用户角色关联表和应用授权表。

教练、代理、家长本身就是业务实体。

我们直接在各自的业务表中增加 userid 字段，将微搭认证身份与业务实体关联起来。

## 1. 教练表：biz_coach

教练表由管理应用中的管理员或教务维护。

| 字段         | 类型建议 | 说明         |
| ---------- | ---- | ---------- |
| \_id       | 系统主键 | 教练业务ID     |
| name       | 文本   | 教练姓名       |
| phone      | 文本   | 手机号        |
| user_id    | 文本   | 微搭认证userid |
| gender     | 文本   | 性别         |
| status     | 文本   | 启用、停用      |
| entry_date | 日期   | 入职日期       |
| remark     | 多行文本 | 备注         |
| created_at | 日期时间 | 创建时间       |
| updated_at | 日期时间 | 更新时间       |

其中：

- `_id` 是教练在业务系统中的唯一标识。
- `phone` 用于联系教练和首次身份匹配。
- `user_id` 用于后续登录身份识别。
- `status` 决定教练是否具有业务访问资格。

## 2. 代理表：biz_agent

| 字段          | 类型建议    | 说明         |
| ----------- | ------- | ---------- |
| \_id        | 系统主键    | 代理业务ID     |
| name        | 文本      | 代理姓名       |
| phone       | 文本      | 手机号        |
| user_id     | 文本      | 微搭认证userid |
| status      | 文本      | 启用、停用      |
| agent_level | 文本      | 代理级别       |
| superior_id | 文本或关联字段 | 上级代理       |
| remark      | 多行文本    | 备注         |
| created_at  | 日期时间    | 创建时间       |
| updated_at  | 日期时间    | 更新时间       |

代理的业务身份与教练身份相互独立。

一个人可以同时拥有教练和代理两种身份。

因此，不能简单地把一个用户只能对应一个业务角色作为系统设计前提。

## 3. 家长表：biz_parent

| 字段           | 类型建议 | 说明         |
| ------------ | ---- | ---------- |
| \_id         | 系统主键 | 家长业务ID     |
| name         | 文本   | 家长姓名       |
| phone        | 文本   | 手机号        |
| user_id      | 文本   | 微搭认证userid |
| status       | 文本   | 启用、停用      |
| relationship | 文本   | 与学员关系      |
| remark       | 多行文本 | 备注         |
| created_at   | 日期时间 | 创建时间       |
| updated_at   | 日期时间 | 更新时间       |

家长通过微信授权手机号登录家长小程序。

首次登录时，通过手机号匹配家长记录，完成userid绑定。

后续则通过userid识别家长身份。

## 4. 身份字段的约束

这三个业务表虽然都增加了 `user_id`，但需要明确以下规则：

- 同一张业务表中，一个有效 userid 只能对应一条业务记录。
- 同一条业务记录只能绑定一个有效 userid。
- 同一个 userid 可以同时出现在教练表和代理表中。
- 未完成绑定的业务记录，`user_id` 可以为空。
- 停用业务记录后，即使 userid 仍然存在，也不能继续进入对应工作台。

这里不要求在三张表之间对 userid 建立全局唯一约束，因为一个人可以同时拥有多个业务身份。

# 七、三个应用的身份识别流程

完成业务表设计后，三个应用的身份识别逻辑就比较清晰了。

## 1. 管理应用

管理应用只允许内部用户访问。

由微搭平台负责内部用户认证和应用权限控制。

进入管理应用后，根据平台分配的角色和数据权限，区分管理员和教务人员。

管理员和教务人员负责维护机构核心业务数据。

## 2. Web工作应用

Web工作应用面向教练和代理。

用户通过手机号验证码登录后，系统从微搭认证上下文获取 userid。

分别查询：

- `biz_coach`：根据 userid 查找启用的教练记录。
- `biz_agent`：根据 userid 查找启用的代理记录。

根据查询结果展示工作台入口：

| 教练身份 | 代理身份 | 首页展示        |
| ---- | ---- | ----------- |
| 有    | 无    | 教练工作台       |
| 无    | 有    | 代理工作台       |
| 有    | 有    | 教练工作台、代理工作台 |
| 无    | 无    | 无权访问提示      |

如果同时具有两种身份，用户可以自主选择进入哪个工作台。

进入教练工作台后使用教练布局和教练菜单；进入代理工作台后使用代理布局和代理菜单。

这里的菜单差异主要解决不同业务角色的界面组织问题，并不代表真正的数据安全边界。

实际业务数据仍然需要通过微搭数据权限和必要的业务校验进行保护。

## 3. 家长小程序

家长小程序面向家长。

用户通过微信授权手机号登录后，系统根据 userid 查询 `biz_parent`。

如果存在启用的家长记录，则允许进入家长端。

如果没有对应记录，或者家长状态为停用，则拒绝进入。

# 八、刷新页面后如何恢复用户身份？

还有一个实际问题：

微搭全局变量可以保存当前用户的业务身份，但是浏览器刷新后，全局变量可能丢失。

因此，我们不能把全局变量当作身份数据的唯一来源。

需要区分三个层次：

| 信息   | 来源                             | 是否需要重新获取 |
| ---- | ------------------------------ | -------- |
| 认证身份 | 微搭认证上下文                        | 刷新后重新获取  |
| 业务身份 | biz_coach、biz_agent、biz_parent | 刷新后重新查询  |
| 页面状态 | 全局变量                           | 可以重新初始化  |

我们的设计是：

1. 用户进入应用后，获取微搭当前认证身份。
2. 根据 userid 查询业务表。
3. 确认业务身份及状态。
4. 将查询结果写入全局变量，供当前应用运行期间使用。
5. 页面刷新后，重新执行身份初始化流程。

不能只在应用首页执行一次身份识别。

因为用户可能直接刷新教练工作台页面，也可能通过收藏链接直接访问某个业务页面。

因此，工作台入口和必要的业务页面也需要具备身份恢复与检查能力。

全局变量只是运行时缓存，业务表才是业务身份的事实来源。

另外，网络异常、数据源查询失败和用户没有业务身份是三种不同情况，不能把查询失败直接当作无权限，也不能在无法完成验证时放行。

# 本篇架构总结

通过这套设计，我们没有改变微搭原有的用户认证和数据权限规则，而是通过业务职责划分和身份绑定机制，适应了平台的能力边界。

最终形成以下架构原则：

1. **核心人员内部化**：管理员和教务使用内部用户，管理机构核心数据。
2. **业务参与者外部化**：教练、代理和家长使用外部用户，不占用稀缺的内部用户授权。
3. **主数据与过程数据分离**：机构主数据由内部用户维护，业务过程数据由外部用户产生。
4. **手机号与业务身份分离**：手机号负责首次身份匹配，userid 负责后续认证身份关联。
5. **业务实体直接关联认证身份**：教练、代理、家长业务表增加 user_id，不额外建设复杂的统一用户授权体系。
6. **特殊更新由云函数处理**：通过服务端校验和具有相应权限的身份完成外部用户无法直接执行的数据更新。
7. **全局变量只做缓存**：刷新后从认证上下文和业务表恢复身份。
8. **平台权限与业务角色分离**：微搭负责认证和数据访问边界，业务系统负责识别教练、代理和家长的业务身份。

这套设计的价值在于：我们没有为了适应业务而绕开平台规则，也没有为了适应平台而把业务系统设计得过于复杂。

**真正好的低代码架构，不是把平台所有功能都用一遍，而是理解平台的边界，再通过合理的业务设计，让平台能力恰好服务于业务需求。**

下一篇，我们将在这套身份架构的基础上，继续设计英语教学平台的核心业务数据模型。
