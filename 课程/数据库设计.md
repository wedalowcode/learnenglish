# 从零设计英语教学管理平台的数据库：六大业务模块与核心数据表

上一篇文章，我们介绍了准备研发的英语教学管理平台。

这是一款面向中小型英语培训机构的软件，涉及老板、教务、管理员、教师、家长和代理六种角色，覆盖客户开发、学员报名、教师管理、课程排课、教学训练、学习报告、课时管理和教师结算等业务。

当我们准备真正开发这款软件时，首先要解决一个问题：

**这么多角色、这么多业务，数据库应该如何设计？**

如果只是开发一个简单的信息管理系统，可能只需要用户表、商品表、订单表，就能完成基本的增删改查。

但真实业务系统远没有这么简单。

例如，一名学员可能有多个家长，一名教师可能负责多个学员，一名学员可能购买多次课程，每次课程又会产生教学记录、学习报告和课时扣减记录。

这些数据之间存在复杂的关联。

如果数据库设计不合理，后续开发就会不断出现重复数据、数据不一致、业务关系混乱等问题。

这篇文章，我们就从实际业务出发，设计这款英语教学管理平台的数据库。

## 一、先确定数据库设计的整体思路

数据库设计不是看到一个页面，就创建一张表。

正确的做法应该是先分析业务，再识别业务对象，最后确定数据之间的关系。

例如，机构有一个学员管理页面。

这个页面展示学员姓名、年级、联系方式、负责教师、剩余课时等信息。

但这些信息实际上来自不同的业务对象：

- 学员姓名、年级属于学员档案。
- 家长联系方式属于家长档案。
- 负责教师属于教师与学员之间的业务关系。
- 剩余课时属于学员课时账户。
- 课程安排属于排课业务。

如果把这些信息全部放在一张 Student 表里，刚开始开发似乎很方便，但随着业务增加，就会产生大量冗余。

因此，我们先把整个系统划分为六个业务模块。

| 业务模块 | 核心业务 | 主要数据对象 |
|---|---|---|
| 系统基础管理 | 账号、角色、权限、机构配置 | 用户、角色、权限 |
| 招生与客户管理 | 客户线索、跟进、代理、报名 | 客户、跟进记录、报名 |
| 学员与教师管理 | 学员档案、教师档案、师生关系 | 学员、教师、关系记录 |
| 教学与课程管理 | 排课、授课、训练、复习、报告 | 课程、训练任务、学习记录 |
| 课时与财务管理 | 订单、收款、课时账户、教师结算 | 订单、流水、结算单 |
| 家长服务 | 家长账号、课程记录、学习反馈 | 家长、家长学员关系 |

这里需要特别注意：

这六个模块是按照业务职责划分的，并不意味着每个模块只能使用自己的数据表。

例如，教师授课会涉及教师表、学员表、课程表、教学记录表和课时流水表。

真正的业务系统，往往是多个模块共同维护一条业务链。

## 二、系统基础管理：解决谁能登录、谁能操作的问题

任何一个管理系统，都需要统一的账号管理和权限控制。

这里首先要区分两个概念：

**用户账号不等于业务人员档案。**

例如：

- 教师有自己的教师档案，也需要一个登录账号。
- 家长有自己的家长档案，也需要一个登录账号。
- 代理有自己的代理档案，也需要一个登录账号。

如果直接把教师信息、家长信息和账号信息混在一起，后续账号停用、人员离职、重新合作时，就很难维护。

因此，系统基础管理建议设计以下数据表。

| 数据表 | 主要用途 |
|---|---|
| users | 系统登录账号 |
| roles | 系统角色 |
| permissions | 系统权限 |
| user_roles | 用户与角色关联 |
| role_permissions | 角色与权限关联 |
| departments | 机构部门或组织结构 |
| system_settings | 系统配置 |
| audit_logs | 重要操作审计记录 |
| notifications | 系统消息通知 |

### 1. 用户表 users

保存所有能够登录系统的账号信息。

核心字段：

- id：用户主键
- username：登录账号
- passwordHash：密码哈希
- phone：手机号
- status：账号状态
- lastLoginAt：最后登录时间
- createdAt：创建时间

这里不直接放教师姓名、家长孩子信息等业务字段。

### 2. 角色与权限

系统有六种主要角色：

- 老板
- 教务
- 管理员
- 教师
- 家长
- 代理

但角色与权限不应该简单地写死在代码里。

建议使用三张表：

- roles：定义角色。
- permissions：定义系统操作权限。
- role_permissions：定义角色可以执行哪些操作。

例如，教师可以查看自己的课程、提交教学记录；家长可以查看孩子的学习报告；代理可以录入自己开发的客户。

除了功能权限，还需要控制数据范围。

例如，教师只能查看自己负责的学员，家长只能查看与自己建立关联的孩子，代理只能查看授权范围内的客户。

因此，权限控制不能只依赖前端是否显示按钮，还必须在服务端进行验证。

### 3. 人员档案与账号关联

建议将业务人员档案独立设计：

| 数据表 | 主要用途 |
|---|---|
| teachers | 教师档案 |
| parents | 家长档案 |
| agents | 代理档案 |

这些档案通过 userId 与 users 建立关联。

这样即使一个教师暂时停止合作，也可以停用账号、保留教师档案和历史授课记录。

如果未来重新合作，也不需要重新创建一个教师身份。

## 三、招生与客户管理：记录客户从哪里来、如何成交

招生业务的核心不是简单地记录一个家长的手机号，而是完整记录客户从产生意向到报名成交的过程。

建议设计以下数据表：

| 数据表 | 主要用途 |
|---|---|
| customers | 客户线索 |
| customer_follow_ups | 客户跟进记录 |
| customer_assignments | 客户分配及归属变更记录 |
| registrations | 学员报名记录 |
| orders | 课程购买订单 |
| payments | 实际收款记录 |

### 1. 客户表 customers

保存潜在客户的基本信息。

主要字段：

- id：客户 ID
- name：客户联系人姓名
- phone：联系电话
- source：客户来源
- acquiredByAgentId：最初获客代理
- ownerAgentId：当前维护代理
- status：客户状态
- createdAt：创建时间

这里有一个容易忽略的问题：

**最初获客的人，不一定是最后成交的人，也不一定是当前维护客户的人。**

例如，客户最初由代理 A 开发，后来转交给代理 B 维护，最终由机构内部人员完成报名。

如果只在客户表中保存一个 agentId，就无法完整记录客户归属的变化。

因此，需要通过 customer_assignments 记录客户归属和负责人变更历史。

### 2. 客户跟进记录 customer_follow_ups

客户从第一次接触到最终报名，可能经历多次沟通。

每次沟通都应该形成独立记录。

主要字段：

- customerId：所属客户
- followUpUserId：跟进人员
- content：沟通内容
- followUpType：沟通方式
- nextFollowUpAt：下次跟进时间
- createdAt：跟进时间

这样就能还原客户的整个跟进过程。

### 3. 报名记录 registrations

客户决定报名后，需要建立正式的报名记录。

报名记录与客户线索不是同一个概念。

一个客户可能有多个孩子，也可能为同一个孩子购买不同阶段的课程。

因此，报名记录应该关联具体学员，而不是直接把所有报名信息写在客户表里。

### 4. 订单与收款分离

订单表示客户购买了什么，收款表示机构实际收到了多少钱。

例如：

家长购买了一份价值 3000 元的课程订单，可能分两次付款。

那么：

- orders 保存一笔 3000 元的订单。
- payments 保存两笔实际收款记录。

不能因为创建了订单，就直接认为机构已经收到全部款项。

只有收款确认后，才能按照业务规则为学员增加可用课时。

## 四、学员与教师管理：建立人与人之间的业务关系

这是整个系统最基础、也最容易设计错误的部分。

### 1. 学员表 students

学员是实际接受教学服务的人。

主要字段：

- id：学员 ID
- name：学员姓名
- gender：性别
- grade：年级
- school：学校
- textbook：使用教材
- status：学员状态

这里不直接保存家长手机号，也不直接保存教师姓名。

因为一个学员可能有多个家长，也可能在不同阶段由不同教师负责。

### 2. 家长表 parents

家长是学员的监护人或家庭联系人。

主要字段：

- id：家长 ID
- name：家长姓名
- phone：联系电话
- userId：关联登录账号

### 3. 家长与学员关系表 parent_students

家长与学员之间不是简单的一对一关系。

例如：

- 一个孩子可以关联爸爸和妈妈。
- 一个家长可以管理多个孩子。
- 多个家庭成员可能共同关注一个孩子。

因此，应该通过中间表建立多对多关系。

主要字段：

- parentId：家长 ID
- studentId：学员 ID
- relationship：关系类型
- isPrimary：是否主要联系人
- createdAt：关联时间

### 4. 教师与学员关系表 teacher_students

教师和学员之间也需要独立的关系表。

主要字段：

- teacherId：教师 ID
- studentId：学员 ID
- status：关系状态
- startDate：开始负责日期
- endDate：结束负责日期

为什么不直接在 students 表中增加 teacherId？

因为教师可能负责多个学员，一个学员也可能在不同阶段由不同教师负责。

通过独立关系表，可以保存师生关系的建立、暂停和结束历史。

需要注意，教师与学员关系表示业务上的负责关系，而每一节课程还需要单独保存实际授课教师。

不能因为后来更换了负责教师，就把历史课程的授课教师一起修改。

## 五、教学与课程管理：系统最核心的业务模块

这部分是整个英语教学管理平台最重要的内容。

机构真正交付给家长的不是一条订单记录，而是持续发生的教学服务。

因此，需要围绕课程、教学任务、训练记录和学习报告建立完整的数据关系。

建议设计以下数据表：

| 数据表 | 主要用途 |
|---|---|
| courses | 课程实例 |
| schedule_requirements | 学员排课需求 |
| teacher_availabilities | 教师可授课时间 |
| schedule_plans | 周期或批量排课计划 |
| course_records | 实际授课记录 |
| wordbooks | 单词词库 |
| words | 基础单词 |
| wordbook_words | 词库与单词关联 |
| student_wordbooks | 学员词库授权 |
| wordbook_requests | 教师词库申请 |
| training_tasks | 教学训练任务 |
| training_records | 单词训练记录 |
| articles | 文章资源 |
| article_sentences | 文章句子 |
| article_training_records | 文章训练记录 |
| review_records | 单词复习记录 |
| review_plans | 学习复习计划 |
| course_reports | 课程学习报告 |

### 1. 课程表 courses

课程是教务管理的核心对象。

每一节课程都应该是一条独立记录。

主要字段：

- id：课程 ID
- studentId：学员 ID
- teacherId：实际授课教师
- courseType：课程类型，例如体验课、正式课
- startTime：开始时间
- endTime：结束时间
- meetingUrl：线上会议地址
- status：课程状态
- schedulePlanId：所属排课计划
- createdAt：创建时间

这里要注意：

课程类型和课程状态是两个不同的概念。

课程类型用于区分体验课和正式课。

课程状态用于表示待上课、已完成、已取消等业务状态。

不能把两者混在一个字段中。

### 2. 排课计划

对于培训机构来说，排课不仅有单次安排，还存在大量周期排课。

例如：

某个学员每周一、三、五晚上 19:00 上课，持续三个月。

如果每次都人工创建课程，效率会很低。

因此可以通过 schedule_plans 保存周期排课规则，再根据规则生成具体课程实例。

同时，学员的可上课时间和教师的可授课时间也需要独立记录。

排课时，系统需要检查：

- 教师是否处于可授课状态。
- 教师在对应时间是否有其他课程。
- 学员在对应时间是否有其他课程。
- 教师是否请假。
- 是否超过教师每日或每周授课负荷。

需要强调，排课计划只是生成课程的依据，真正发生的课程仍然应该保存在 courses 中。

### 3. 词库与单词

单词训练是本系统的重要教学功能。

首先需要区分三个概念：

- Word：一个基础单词。
- Wordbook：一个词库。
- WordbookWord：某个词库包含哪些单词。

为什么需要拆成三张表？

因为同一个单词可能同时出现在多个词库中。

例如，单词 apple 可能出现在人教版三年级词库，也可能出现在自然拼读词库。

如果把单词直接存储在词库表中，就会产生大量重复数据。

因此：

words 保存基础单词信息，wordbooks 保存词库信息，wordbook_words 负责建立词库和单词之间的多对多关系。

词库的顺序也应该由 wordbook_words 独立维护。

### 4. 学员词库授权

不是所有教师都可以随意使用所有词库。

教师可能需要先为学员申请某个词库，再由管理员审核。

因此，需要区分：

- wordbook_requests：教师申请记录。
- student_wordbooks：学员已经获得的词库授权。

申请不等于授权，审核通过后才能正式使用。

这也是一个典型的业务状态流转问题。

### 5. 单词训练记录

单词训练不是简单地把一个单词标记为认识或不认识。

系统需要知道：

- 哪个学员参加了训练？
- 哪位教师组织了训练？
- 本次训练使用了哪个词库？
- 训练包含哪些单词？
- 每个单词训练了几次？
- 最终掌握情况如何？

因此，训练任务和训练记录需要分开。

training_tasks 表示一次完整训练任务，training_records 表示任务中每个单词的实际训练情况。

这样才能支持历史训练查询、学习统计和后续复习安排。

### 6. 复习体系

系统需要记录学生哪些单词还没有掌握，以及下一次什么时候需要复习。

这里需要特别注意：

莱特纳盒子复习法和 21 天记忆法是两套不同的复习机制。

不能把它们简单地设计成一个复习状态字段。

建议保留独立的复习计划和复习记录，并通过复习类型区分不同算法。

莱特纳盒子需要记录单词所在盒子、下次复习时间以及教师手动调整情况。

21 天记忆法则需要记录独立的训练日期、复习阶段和完成情况。

这样才能避免两套复习规则互相覆盖。

### 7. 课程学习报告

每节课程完成后，系统需要形成学习报告。

报告应该关联具体课程，并记录本次教学内容、训练成果、掌握情况和后续学习建议。

家长查看的不是教师随意填写的一段文字，而是能够追溯到实际教学活动的学习结果。

## 六、课时与财务管理：让每一笔钱都有依据

培训机构有两个重要的财务对象：

一个是学员购买的课时，另一个是教师完成课程后应获得的课时费。

这两件事都与课程有关，但不能直接合并。

建议设计以下数据表：

| 数据表 | 主要用途 |
|---|---|
| student_hour_accounts | 学员课时账户 |
| student_hour_transactions | 学员课时变动流水 |
| teacher_pay_rules | 教师课时费规则 |
| teacher_lesson_fees | 单节课程教师费用明细 |
| teacher_settlements | 教师月度结算单 |
| teacher_settlement_items | 结算单明细 |
| teacher_settlement_adjustments | 结算调整记录 |
| teacher_payments | 教师付款记录 |

### 1. 学员课时账户

student_hour_accounts 保存学员当前可用课时。

例如：

某学员购买了 50 节课程，已经上了 12 节，那么当前剩余 38 节。

但系统不能只保存一个余额数字。

还必须有 student_hour_transactions 记录每次课时变化。

例如：

- 购买课程增加 50 节。
- 完成课程扣减 1 节。
- 误扣后冲正返还 1 节。
- 机构赠送课程增加 2 节。

每一次变动都要有来源、有时间、有操作人。

**账户余额是当前结果，流水才是变化依据。**

### 2. 教师课时费规则

不同教师可能有不同的课时费标准。

例如：

- 教师 A：体验课 30 元/节，正式课 50 元/节。
- 教师 B：体验课 40 元/节，正式课 60 元/节。

因此，需要 teacher_pay_rules 保存教师课时费规则。

规则还应该记录生效时间。

如果教师后续调整单价，历史课程仍然应该按照当时生效的规则计算，不能因为修改了当前单价，就导致以前的结算金额发生变化。

### 3. 单节课程费用明细

每节课程实际完成后，系统根据对应教师和课程类型生成教师费用明细。

teacher_lesson_fees 保存：

- 课程 ID
- 教师 ID
- 课程类型
- 计费规则
- 当时适用的单价
- 实际计费金额
- 计费状态

这里必须保存单价和金额快照。

不能在月底结算时，再拿教师当前的单价重新计算历史课程。

### 4. 教师月度结算

每个月，机构需要与兼职教师核对实际授课数量和课时费。

teacher_settlements 保存结算单主信息。

teacher_settlement_items 保存结算单中的每节课程明细。

teacher_payments 保存实际付款记录。

这样就可以支持：

- 月度课时费统计。
- 教师核对结算单。
- 结算金额调整。
- 全额付款。
- 部分付款。
- 分批付款。
- 付款记录追踪。

结算单不等于付款记录。

机构确认应该支付多少钱，与机构实际支付了多少钱，是两个不同的业务事实。

## 八、数据库设计中最值得关注的五个问题

对于一个真实项目来说，数据库表创建出来并不代表设计完成。

还需要考虑业务数据在各种情况下是否能够保持一致。

### 1. 不要把所有信息塞进一张表

例如，不要把学员姓名、家长电话、教师姓名、课程时间和课时余额全部塞进 students 表。

这些信息属于不同业务对象。

应该根据业务实体建立独立的数据表，再通过关联关系连接。

这样才能支持后续业务扩展。

### 2. 重要业务必须保留历史记录

例如：

- 学员更换教师，应该保留原来的师生关系。
- 教师调整课时费，不能影响历史课程费用。
- 客户转交代理，应该保留归属变化记录。
- 学员课时发生变化，应该保留完整流水。

对于真实业务系统来说，当前状态固然重要，但历史变化同样重要。

### 3. 业务状态不能随意修改

例如，一节课程可能经历：

待上课 → 已完成。

也可能经历：

待上课 → 已取消。

已完成的课程不能随意修改回待上课状态，更不能通过重复提交完成操作，导致学员被重复扣课、教师被重复计费。

因此，重要业务操作需要有明确的状态流转规则，并在服务端进行校验。

### 4. 金额和课时必须保持准确

金额字段不能使用普通浮点数随意计算。

数据库中应该使用 Decimal 等精确数值类型，或者统一使用整数分保存金额。

课时也不能仅仅依靠前端计算。

课程完成、学员扣课、教师计费等操作需要在服务端协调处理，并通过事务、唯一约束和幂等机制防止重复执行。

### 5. 权限必须落实到数据访问层

家长只能查看自己关联的学员。

教师只能查看自己负责范围内的教学数据。

代理只能查看授权范围内的客户。

这些规则不能仅仅依赖前端隐藏菜单或按钮。

每次查询、修改和业务操作，都必须在服务端验证当前用户身份、角色和数据归属。

## 九、总结：数据库设计决定了软件能够走多远

这次英语教学管理平台的数据库设计，核心不是创建多少张表，而是把真实业务中的人物、关系、过程和结果准确地表达出来。

我们可以把整个系统理解为三个层次：

**第一层：基础数据。**

用户、教师、家长、代理、学员、词库和单词等基础信息。

**第二层：业务过程。**

客户跟进、报名、排课、授课、单词训练、复习和结算等业务活动。

**第三层：业务结果。**

学习报告、学员课时余额、教师应付费用、实际付款和经营统计。

这三层数据相互关联，才能构成一个真正可运行的业务系统。

对于全栈开发者来说，这也是一个很好的实践案例。

因为数据库设计不是把页面上的字段搬到数据库，而是理解业务之后，把业务对象、业务关系和业务规则转换成数据结构。
